MCU-Insight

What an ESP-IDF build costs, what the device actually does at runtime, and whether the last change made it worse.

Usage guideCase studyExample report

What it answers

What does this build cost

Flash, static DRAM, IRAM and the app partition, per component, from the linker map and the binary. No board needed.

What is the device doing

Stack high-water marks per task, the smallest free heap and the largest free block, per-core idle share, latency percentiles, sleep residency: whatever the firmware publishes.

Did the change make it worse

Budget rules that bound a value or a slope, a comparison against a stored baseline, and an evidence pack when something needs explaining.

Four steps on a new project

1
run in mcu-insight\

Copy the device agent in

One ESP-IDF component. ESP-IDF wants components inside the project tree, so this copies it there and tells you what it wrote.

python tools/sync_firmware.py ..\My-Project

the project before

My-Project\
  CMakeLists.txt
  main\main.c

the same project after

My-Project\
  CMakeLists.txt
  components\            <- created by the command
    mcu_telemetry\       <- created by the command
      CMakeLists.txt
      include/mcu_telemetry.h
      mcu_telemetry.c
  main\main.c

Nothing here is created by hand. The command makes components\ and mcu_telemetry\ if they are missing. The argument has to be the project root, the directory that holds CMakeLists.txt; given anything else it stops and says it does not look like an ESP-IDF project.

One line in the project's main/CMakeLists.txt, or the header will not resolve:

# main/CMakeLists.txt
idf_component_register(
    SRCS "main.c"
    INCLUDE_DIRS "."
    REQUIRES driver nvs_flash freertos mcu_telemetry)

and then build and flash, from the firmware project:

cd ..\My-Project
idf.py -p COM19 flash monitor

run in mcu-insight\

Frames are appended to a SQLite file, so every command after this reads the file instead of the board. Log lines on the same port are ignored.

4
run in mcu-insight\

Look at it

One self-contained HTML file: data inlined, charts hand-written SVG, no server, no CDN, no script.

python -m mcu_insight report --db captures/board.db --config budgets/my-project.json --out report.html

The command writes report.html into the directory you ran it from. Double-click it, or open it from the file manager. The report linked here was made the same way, from the capture committed in this repository: docs/report-demo.html

Where everything lives

All four commands run in the tool repository. Your firmware project is a neighbour: step 1 copies the agent into it, and the report step reads that project's build output.

mcu-insight\   the tool, run every command here
  mcu_insight\    the package
  tools\          sync_firmware.py, fault_matrix.py
  budgets\        your budget files go here
  captures\       captured telemetry lands here (*.db)
  docs\           index.html, report-demo.html, the guides
My-Project\   your firmware, next to the tool
  components\
    mcu_telemetry\   <- step 1 writes this directory
      CMakeLists.txt
      include/mcu_telemetry.h
      mcu_telemetry.c
  main\main.c      <- the five lines from step 1
  build\           .map and .bin are read from here

What you add to your own project

Five lines of C, and one JSON file that says what the budgets are and what the metrics mean.

#include "mcu_telemetry.h"

static const mcu_telemetry_config_t telemetry = {
    .device = "my-board",
    .firmware = FW_REVISION,
    .report_period_ms = 5000,
};

ESP_ERROR_CHECK(mcu_telemetry_start(&telemetry));
mcu_telemetry_register_task("control", TASK_STACK_CONTROL);
mcu_telemetry_set_custom_int("loop_jitter_us", jitter);
mcu_telemetry_histogram_add("infer", latency_us);
{
  "rules": [
    {"metric": "heap.min", "min": 100000, "stat": "min"},
    {"metric": "heap.free", "min_rate_per_s": -64, "min_span_ms": 60000},
    {"metric": "task.*.stack_free_min", "min": 256, "stat": "min"},
    {"metric": "custom.infer_p99_us", "max": 5000, "stat": "max"}
  ],
  "baseline": {"path": "my-project-baseline.json", "max_change_pct": 20}
}

What a diagnosis looks like

The tool does not guess. It collects a numbered evidence pack, you hand that to any model, and it checks the answer that comes back.

evidence pack (diagnose)

MCU-INSIGHT EVIDENCE PACK
[E1] device esp32-signal-processor (firmware dev)
[E2] capture 21 frames over 1 boot session(s) from captures\fault-heap.db
[E3] provenance FAULT heap, a heap leak is injected on purpose. The file name says so, so unless it was renamed, what follows is deliberate test behaviour, not a regression in the application code.
[E4] budget file budgets/signal.json
[E5] baseline capture: not recorded -- the file predates the capture shape. The one duration it carries is uptime_ms 248,337, the point the device had reached when the snapshot was taken
[E6] note the baseline was taken after 248 s of uptime and this capture holds 95 s of steady state. A level delta on a high-water mark carries part of that difference, so the rates are the ones to compare; a baseline saved from now on records its own span and settles it
[E7] baseline revision unknown: the baseline file records no revision, so the diff range has to be given with --diff-since
[E8] VIOLATION heap.free: falls at -956.9 per second, slope >= -64/s over >= 60 s of steady state
...

the model's answer

The deliberately injected leak in main/main.c: s_leak_sink = malloc(2048) executed once per main
loop iteration while s_fault == FAULT_HEAP [E98]. The pack's own provenance states the fault is
injected on purpose [E3], the capture is taken by tools/fault_matrix.py --port COM19 [E4], and the
fault is armed at run time over the console, where FAULT heap means "leak 2 KB per loop" [E98].

checked against the pack (audit)

MCU-INSIGHT ANSWER AUDIT
citations   : 50 distinct of 126 in the pack (99 available)
unknown id  : none
unknown name: none
uncited line: 0 (a warning, not an error)

RESULT: OK

What the HTML report contains

Five blocks, and every one of them is generated from the capture.

Checksthe verdict, every rule, and any rule that was not judged
Baseline changeswhat moved since the baseline snapshot, coloured only when the worrying direction is known
Metric trendsthe metrics that moved most, one card each, with every reboot marked
Build resourcesflash, static DRAM, IRAM, partition use, top components
Fault injection matrixwith a fault directory, whether the checks caught each injected fault

MCU-Insight

代码仓库 完整指南 三轮诊断案例 报告示例

这东西是干什么的

一共就四件事，没别的。

  • 把一个小组件拷进你的 ESP-IDF 工程，让固件每隔几秒报一次自己的状态
  • 跑一条命令，得到一份给人看的 HTML 报告：固件占多少 Flash 和 RAM、每个任务还剩多少栈、堆最少剩多少、推理慢不慢
  • 出问题的时候，得到一份证据包：所有已知事实，一条条编号，直接粘给任何 AI
  • 再把 AI 的诊断拿回来核对：它会指出 AI 引用了根本不存在的证据

不用联网、不用注册、不用仪器。

你只需要动三个地方，别的都不用改

  • My-Project/main/main.c —— 加 3 行，下面标了每一行放哪
  • My-Project/main/CMakeLists.txt —— 加一个名字 mcu_telemetry
  • mcu-insight/budgets/my-board.json —— 新建这个文件，写你的红线

B. 要你自己粘 3 行，看板子的真实数据

先说一句：一开始你什么都不用盯。先跑一次，报告会告诉你哪里紧张；紧张的地方再回来加一行。

1
在 mcu-insight\ 目录里运行

第一步：把组件拷进你的工程

就一条命令。它把 agent 拷进你的工程，并告诉你写了哪些文件。

python tools/sync_firmware.py ..\My-Project

你的工程，运行前

My-Project\
  CMakeLists.txt
  main\main.c

运行后

My-Project\
  CMakeLists.txt
  components\            <- 由这条命令创建
    mcu_telemetry\       <- 由这条命令创建
      CMakeLists.txt
      include/mcu_telemetry.h
      mcu_telemetry.c
  main\main.c

没有任何东西要你手工建：components\ 或 mcu_telemetry\ 不存在，命令会自己创建。参数必须是工程根目录，也就是放 CMakeLists.txt 的那一层。

2
在 My-Project\ 目录里运行

第二步：改 main.c，最少 3 行

三行的位置下面都标了。你原来的业务代码一个字都不用改。

/* 第 1 行：文件最上面，和其他 #include 放一起 */
#include "mcu_telemetry.h"

/* 第 2 行：app_main 外面，文件里任意位置 */
static const mcu_telemetry_config_t telemetry = {
    .device = "my-board",      /* 给板子起个名字 */
    .report_period_ms = 5000,  /* 每 5 秒上报一次 */
};

void app_main(void)
{
    /* ... 你原本的初始化 ... */

    /* 第 3 行：硬件起来之后 */
    ESP_ERROR_CHECK(mcu_telemetry_start(&telemetry));

    /* 下面还是你原来的业务代码，一行都不用改 */
}

这 3 行写完，下面这些它自动就报，不用你写代码：

  • 堆：现在剩多少、历史最少剩多少、最大可分配块是多少
  • 每个任务的栈还剩多少（开了下面第一个开关，连 httpd / mqtt / wifi 这些任务也会自动出现）
  • 每个 CPU 核的空闲占比（开了第二个开关）
  • 睡眠时间占比（开了第三个开关）
  • 串口重试次数（它自己数，用来发现丢数据）

那三个开关在 idf.py menuconfig 里打开，是配置，不是代码：

CONFIG_FREERTOS_USE_TRACE_FACILITY=y       自动发现工程里所有任务
CONFIG_FREERTOS_GENERATE_RUN_TIME_STATS=y 每核空闲占比
CONFIG_PM_ENABLE=y                         睡眠占比

想要更细，再加这几行（可选，不加也能跑）：

/* 可选：想知道某个任务的栈用了百分之多少，任务建好之后加一行 */
xTaskCreate(control_task, "control", 4096, NULL, 2, NULL);
mcu_telemetry_register_task("control", 4096);   /* 名字要和 xTaskCreate 里一致 */

/* 可选：你自己的数值，在它算出来的那一行下面加 */
mcu_telemetry_set_custom_int("loop_jitter_us", jitter);

/* 可选：任何函数的耗时分布，在调用处加一行，自动出 p50 / p99 / 最大 / 最小 */
mcu_telemetry_histogram_add("infer", latency_us);

第六步：写下你的红线

在工具仓库里新建一个文件。这是唯一需要你自己写的东西：你的工程不许越过的数值。heap.min 是最小空闲堆，min_rate_per_s 是它每秒最多能掉多少。

{
  "rules": [
    {"metric": "heap.min", "min": 100000, "stat": "min"},
    {"metric": "heap.free", "min_rate_per_s": -64, "min_span_ms": 60000},
    {"metric": "task.*.stack_free_min", "min": 256, "stat": "min"},
    {"metric": "custom.infer_p99_us", "max": 5000, "stat": "max"}
  ],
  "baseline": {"path": "my-board-baseline.json", "max_change_pct": 20}
}

第八步：出证据包，让 AI 来讲

工具不猜。它把所有已知事实写成一份带编号的证据包就停手。你把这份包粘给任何 AI，再把答案拿回来核对。

python -m mcu_insight diagnose --db captures/board.db --config budgets/my-board.json --out prompt.txt

1. 它写出的证据包（diagnose）

MCU-INSIGHT EVIDENCE PACK
[E1] device esp32-signal-processor (firmware dev)
[E2] capture 21 frames over 1 boot session(s) from captures\fault-heap.db
[E3] provenance FAULT heap, a heap leak is injected on purpose. The file name says so, so unless it was renamed, what follows is deliberate test behaviour, not a regression in the application code.
[E4] budget file budgets/signal.json
[E5] baseline capture: not recorded -- the file predates the capture shape. The one duration it carries is uptime_ms 248,337, the point the device had reached when the snapshot was taken
[E6] note the baseline was taken after 248 s of uptime and this capture holds 95 s of steady state. A level delta on a high-water mark carries part of that difference, so the rates are the ones to compare; a baseline saved from now on records its own span and settles it
[E7] baseline revision unknown: the baseline file records no revision, so the diff range has to be given with --diff-since
...

2. AI 给出的答案

The deliberately injected leak in main/main.c: s_leak_sink = malloc(2048) executed once per main
loop iteration while s_fault == FAULT_HEAP [E98]. The pack's own provenance states the fault is
injected on purpose [E3], the capture is taken by tools/fault_matrix.py --port COM19 [E4], and the
fault is armed at run time over the console, where FAULT heap means "leak 2 KB per loop" [E98].

3. 拿回证据包里核对（audit）

MCU-INSIGHT ANSWER AUDIT
citations   : 50 distinct of 126 in the pack (99 available)
unknown id  : none
unknown name: none
uncited line: 0 (a warning, not an error)

RESULT: OK

想让它用中文回答，加一个参数：

python -m mcu_insight diagnose --db captures/board.db --config budgets/my-board.json --lang zh --out prompt.txt

证据编号 [E12] 和指标名保持工具里的原样，因为它们是标识符，翻译了就对不上；中文的是说明和回答。

它拿回来的诊断固定是这四段：

  • 根因：最可能的那一个，给一个置信度，再列出支撑它的证据编号
  • 其它可能：还有什么会造成同样现象，哪个观察能把它排除
  • 修复：针对根因的最小改动
  • 验证：跑哪条命令、哪个指标该动、大致动多少
python -m mcu_insight audit --pack prompt.txt --answer answer.md

最后一步是核对：答案里每个 [E12] 必须在证据包里真的存在；引用了不存在的编号，直接判失败。

所以它到底值在哪

  • 它看见 AI 看不见的东西。模型能读你的代码，但读不到你板子上：栈剩 512 还是 256 字节、堆最少剩 24KB 还是 4KB、推理 P99 是 30ms 还是 55ms。这些只有量出来才有。
  • 它不让 AI 瞎编。所有事实都带编号，答案必须引用；核对时出现不存在的编号就判失败。没有这一层，诊断只是听起来有道理。
  • 它能回答为什么这次变差了。有基线做对照（版本、采集时长、每个指标的斜率），所以分得清是真的变差了，还是这次只是采得短。

一句话：检测靠规则和统计，解释靠 AI。工具负责拿到证据，AI 负责讲道理，而这两者之间的引用关系可以被机器核对。

最后你手上有什么

跑完整条流程，多出来的是这几样。全部在你自己电脑上，没有云端副本。

  • report.html —— 给人看的：双击打开，一页看完固件占多少、哪里紧张。
  • captures/board.db —— 你自己的数据：以后的分析都读它，不用再插板子。
  • budgets/…-baseline.json —— 给下一次改动：自动对比，告诉你哪一项变差了。
  • prompt.txt 和 answer.md —— 你和 AI 的一来一回：证据包，加它给出的诊断。
  • check 的退出码 —— 给 CI：0 通过、1 不通过，可以直接卡流水线。
